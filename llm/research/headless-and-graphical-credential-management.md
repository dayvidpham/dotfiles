# Mature credential tools still need routing

**Yes: established components cover Qt-first/TUI prompting and encrypted credential storage, but no researched solution automatically routes every prompt across this topology.** Prefer one same-user gpg-agent, packaged pinentry-qt with curses fallback, bounded agent caching, and pass for terminal-first application secrets. Keep a desktop Secret Service where applications require it. Custom password dialogs or remember/unlock checkboxes are unnecessary. Physical niri, private-runtime/private-D-Bus Sunshine/VNC Sway, and boot-persistent tmux nevertheless need explicit environment and prompt-destination policies. The evidence establishes upstream/distribution maturity, not measured adoption or a tested drop-in configuration for this machine ([Pinentry](https://github.com/gpg/pinentry/blob/master/README), [password-store](https://www.passwordstore.org/)).

## Qt already handles fallback and remembering—with limits

**pinentry-qt already supplies curses fallback when compiled with it.** Nixpkgs packaging includes the relevant terminal and Qt Wayland dependencies; verify the locked revision’s build. Crucially, release 1.3.2 chooses GUI mode from environment hints, including the presence of `WAYLAND_DISPLAY` or a graphical `XDG_SESSION_TYPE`. It does not retry curses after Qt initialization fails. **Absent display and stale/unreachable display are different cases.** Terminal-only invocations must remove misleading graphical hints and supply a usable terminal; `GPG_TTY` alone does not force curses ([Qt source](https://github.com/gpg/pinentry/blob/pinentry-1.3.2/qt/main.cpp), [Nixpkgs](https://github.com/NixOS/nixpkgs/blob/master/pkgs/tools/security/pinentry/default.nix)).

Remembering has two independent layers. gpg-agent caches passphrases in RAM without a checkbox: default idle lifetimes are 600 seconds normally and 1,800 seconds for SSH, with 7,200-second maximum lifetimes. Access refreshes idle time, not the maximum. Qt also implements a “Save passphrase in password manager” checkbox. **A Qt dialog can still store through libsecret and GNOME Keyring** when compiled and permitted: its shared cache backend uses Secret Service. Changing the frontend therefore does not remove wallet unlocking or bus dependencies. `no-allow-external-cache` disables that integration, not the internal agent cache ([agent options](https://www.gnupg.org/documentation/manuals/gnupg/Agent-Options.html), [Qt](https://github.com/gpg/pinentry/blob/pinentry-1.3.2/qt/main.cpp), [cache backend](https://github.com/gpg/pinentry/blob/pinentry-1.3.2/pinentry/password-cache.c)).

## Shared credentials do not imply shared session context

A connected headless Sway session is graphical; an SSH/tmux terminal without display access is not. Keep `GPG_TTY` current per pane and refresh existing shells’ environments deliberately: changing tmux’s server environment does not rewrite them. GnuPG forwards several session variables, including Wayland and D-Bus settings, but its standard forwarding list does **not** include `XDG_RUNTIME_DIR`. A private Sway runtime directory therefore is not necessarily transported from client to agent-launched pinentry; verify display socket, runtime directory and bus together ([GnuPG invocation](https://www.gnupg.org/documentation/manuals/gnupg/Invoking-GPG_002dAGENT.html), [forwarded variables](https://github.com/gpg/gnupg/blob/master/common/session-env.c), [child setup](https://github.com/gpg/gnupg/blob/master/agent/call-pinentry.c)).

**SSH-agent requests cannot identify the caller’s display or terminal.** `gpg-connect-agent updatestartuptty /bye` changes shared startup context: useful for sequential switching, but last-update-wins under concurrency. Recommend a designated SSH prompt destination or explicit switching. Independent simultaneous routing requires separate agents or additional session-aware integration, sacrificing simplicity/shared cache. One same-user agent can serve boot-persistent tmux and multiple desktops during a boot; that means shared service lifetime, **not unlimited cache lifetime or reboot-persistent unlocking** ([agent options](https://www.gnupg.org/documentation/manuals/gnupg/Agent-Options.html)).

Likewise, systemd’s user manager is shared, while Secret Service prompts belong to the provider and bus. Globally importing one desktop’s environment merely selects that desktop. Preserve private compositor environments; use explicit canonical credential endpoints where appropriate. Applications needing both a private session bus and shared Secret Service need a considered proxy/bridge or different bus topology—not a blanket bus-variable replacement ([systemd](https://raw.githubusercontent.com/systemd/systemd/main/man/pam_systemd.xml), [Secret Service](https://specifications.freedesktop.org/secret-service-spec/latest-single/)).

## Prefer pass for headless tokens, not implicit integration

**pass plus QtPass is the clearest established CLI/Qt pairing.** pass stores GPG-encrypted files and reuses gpg-agent; QtPass adds a compatible GUI. For GitHub CLI, retrieve a designated token entry and supply `GH_TOKEN` only to the invoked process. The adapter should fail closed on failed decryption or empty output, avoid tracing/logging secrets, and limit token scope. This uses gh’s documented headless interface; environment transport still exposes plaintext to the process and descendants ([password-store](https://www.passwordstore.org/), [gh environment](https://cli.github.com/manual/gh_help_environment)).

**Supplying `GH_TOKEN` neither migrates gh’s stored credentials nor makes gh consult arbitrary Git helpers.** `gh auth setup-git` makes Git use gh, not the reverse. Separate pass-backed Git helpers serve HTTPS Git, not gh’s API-token storage. Current unrestricted `gh auth status` can still inspect stored accounts and touch the keyring; where supported, use `--active --hostname github.com` for the environment-selected account ([setup-git](https://cli.github.com/manual/gh_auth_setup-git), [status implementation](https://github.com/cli/cli/blob/trunk/pkg/cmd/auth/status/status.go)).

## Keep desktop wallets when applications require them

GNOME Keyring, KWallet and KeePassXC are established desktop choices, but **switching to KWallet does not solve headless prompt routing**. KeePassXC offers separate terminal database access; its CLI does not unlock its GUI’s Secret Service database. GNOME Keyring supports stdin unlocking specifically for the login keyring, not arbitrary collections. PAM auto-unlock needs a login password; boot-started Sway or streaming authentication does not inherently provide one. Retaining a desktop provider is reasonable with deliberate pre-unlock/designated-session policy ([KeePassXC](https://github.com/keepassxreboot/keepassxc/blob/develop/docs/man/keepassxc-cli.1.adoc), [KWallet](https://docs.kde.org/stable_kf6/en/kwalletmanager/kwalletmanager/kwallet-using.html), [GNOME daemon](https://github.com/GNOME/gnome-keyring/blob/master/docs/gnome-keyring-daemon.xml), [PAM](https://wiki.gnome.org/Projects/GnomeKeyring/Pam)).

pass/gopass Secret Service bridges exist, but are **niche integrations, not equally established replacements**. Evaluate compatibility and bootstrap behavior before adoption: one pass bridge documents unencrypted attributes; a gopass bridge documents deadlock when pinentry requests its passphrase from the service already waiting for GPG decryption. Disable external caching for that dependency chain and retain independent recovery ([pass bridge](https://github.com/grimsteel/pass-secret-service), [gopass bridge](https://github.com/nikicat/gopass-secret-service)).

## Conclusion

The remaining engineering is session routing, not password collection. Validate Qt on niri and each private Sway session, genuinely display-free terminal fallback, stale-display failure, tmux reattachment, and cache expiry before removing existing glue. These are documentation-based recommendations; local versions and service environments remain unverified.
